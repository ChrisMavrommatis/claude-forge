# Addon — Microsoft 365

Connects the brief to Microsoft 365 via the `claude.ai/Microsoft 365` MCP connector. Outlook email and calendar are wired today; Teams chat, SharePoint, and meeting-availability surfaces are visible on the connector and queued for future investigation rounds.

> **Status — partial.** Email + calendar surfaces live — 7 catalog entries (M365.1–M365.7) backed by real `outlook_email_search` / `outlook_calendar_search` tool calls with measured ~600–800ms latencies. Teams, SharePoint, and meeting-availability surfaces are registered on the same connector but not yet cataloged here — they share one auth and one profile block, so they'll land as additional catalog entries (M365.8+) under this same addon rather than separate addon files.

## Profile shape

Top-level `m365` block in `profile.json`:

```json
{
  "m365": {
    "client_domains": ["example-client.com", "example-client-2.com"],
    "important_senders": ["ceo@example.com"],
    "internal_domains": ["example.com"],
    "dl_addresses": ["team-all@example.com"]
  }
}
```

- `client_domains[]` — external client domains. Drives M365.2 — surfaces inbound email from external client domains in the brief. Empty list = no client filtering. Partial-match by domain (the tool's `sender` param does the `endswith` for us).
- `important_senders[]` — VIP addresses that always surface (no date window). Optional; default empty. Typically added via tailoring nudge, not first-run.
- `internal_domains[]` — internal team domains. Optional; default absent. Opt-in only.
- `dl_addresses[]` — distribution lists the user owns or watches. Optional; default absent. Opt-in only.

No `provider` field — the addon binds to the single registered MCP connector. If a second M365 provider lands later (e.g. a direct Graph adapter), revisit.

## Connection

**`claude.ai/Microsoft 365` MCP** — browser-based OAuth via `/mcp` in Claude Code. Tokens persist in `~/.claude/`; no daily re-auth.

Probe the namespace `mcp__claude_ai_Microsoft_365__*` to detect whether the MCP is registered. An `outlook_email_search(limit=1)` call returns 401 when registered-but-unauthenticated — that's the cue for the auth-needed header (M365.6).

Throughout this catalog the namespace prefix is implied — `outlook_email_search` means `mcp__claude_ai_Microsoft_365__outlook_email_search`.

## Catalog

The full set of read-only Microsoft 365 calls this addon exposes. See [Defaults](#defaults) below for which entries come on automatically. The orchestrator may issue any catalog entry on demand once the user has authenticated.

**Cost grammar.** The summary table carries only the **size** (XS / S / M / L / XL) for at-a-glance triage. The full cost — `<size> · ~Xms · <scaling note>` — lives in each entry's detail block:
- **Size** — t-shirt class for the at-a-glance feel.
- **~Xms** — per-call wall-time estimate. Measured from real `outlook_email_search` calls (`~800ms` baseline).
- **Scaling note** — how the call grows with config (`per domain (parallel)`, `per VIP (parallel)`, etc.).

Placeholders:
- `${currentUser}` — `profile.identity.git.email` (Microsoft 365 typically matches this)
- `${state.last_run}` — from `state.json` (ISO timestamp; the tool accepts natural-language dates too)
- `${profile.m365.client_domains}` — list of external client domains
- `${profile.m365.important_senders}` — list of VIP addresses
- `${profile.m365.internal_domains}` — list of internal team domains
- `${profile.m365.dl_addresses}` — list of distribution-list addresses

### Tool constraints (worth knowing before reading the catalog)

`outlook_email_search` has a few mutual-exclusion rules baked into its schema. The catalog respects them; calling them out here saves re-discovery:

- `recipient` + `folderName` are **incompatible** — choose one. M365.1 uses `recipient` and post-filters Inbox-ness in the orchestrator.
- `recipient` is also incompatible with `mailboxOwnerEmail` and `order`.
- One `sender` per call (no native OR). Multi-domain / multi-VIP queries issue **N parallel calls** and merge in the orchestrator.
- No `isRead` or `isFlagged` filter — orchestrator does post-filter on `isRead` where needed.
- Max `limit=25` per page. Pagination via `nextOffset` or `nextCursor`. The catalog **caps at first page** (25 results per source) to keep the brief snappy.

### Details

#### M365.1 — Unread mail addressed to me

**Cost:** M · ~800ms · one call + orchestrator post-filter.

Mail addressed to `${currentUser}` (To: or Cc:) received since `${state.last_run}`, then filtered for unread. The signature inbox signal — "someone is talking directly to me."

The tool forbids `recipient` together with `folderName` or `order`, so the search is global by recipient and the orchestrator both post-filters for `isRead == false` AND sorts by `receivedDateTime` desc itself.

```
outlook_email_search(
  recipient=${currentUser},
  afterDateTime=${state.last_run},
  limit=25
)
# orchestrator filters: isRead == false, then sorts by receivedDateTime desc
```

Empty render: *"No new unread mail."*

#### M365.2 — Mail from configured client domains

**Cost:** M · ~800ms · **per domain (parallel)** across `${profile.m365.client_domains}`.

Mail from any sender whose domain matches an entry in `${profile.m365.client_domains}`, within the brief window. Read or unread — these surface regardless of triage state (useful when external-client traffic is what your morning hinges on).

The tool's `sender` parameter does partial-match on the address, so passing the bare domain (e.g. `acme.com`) catches every sender from that domain. One call per domain; merge results in the orchestrator. Hidden if `client_domains[]` is empty.

```
# Issued in parallel, one per domain in profile.m365.client_domains[]
outlook_email_search(
  sender="acme.com",
  afterDateTime=${state.last_run},
  limit=25,
  order="newest"
)
```

Empty render: *"No client-domain mail since you left."*

#### M365.3 — Mail from important senders (VIPs)

**Cost:** M · ~800ms · **per VIP (parallel)** across `${profile.m365.important_senders}`.

Mail from any address in `${profile.m365.important_senders}`, no date window — VIPs always surface. One call per address; merge in the orchestrator. Only useful once the list is populated — the barista doesn't ask for VIPs at onboarding (would blow the four-question cap), so this entry is opt-in and surfaced via a tailoring nudge later.

```
# Issued in parallel, one per address in profile.m365.important_senders[]
outlook_email_search(
  sender="ceo@example.com",
  limit=25,
  order="newest"
)
```

Empty render: *"No mail from VIPs."*

#### M365.4 — Mail from internal team domains

**Cost:** M · ~800ms · **per domain (parallel)** across `${profile.m365.internal_domains}`. Requires `profile.m365.internal_domains[]`.

Mirror of M365.2 for in-house chatter — surfaces mail from configured internal-team domains in the brief window. Opt-in: most users start without this and add it once the tailoring nudge surfaces it.

```
# Issued in parallel, one per domain in profile.m365.internal_domains[]
outlook_email_search(
  sender="example.com",
  afterDateTime=${state.last_run},
  limit=25,
  order="newest"
)
```

Empty render: hidden when not configured.

#### M365.5 — Distribution-list mail

**Cost:** M · ~800ms · **per DL (parallel)** across `${profile.m365.dl_addresses}`. Requires `profile.m365.dl_addresses[]`.

Mail addressed to distribution lists the user owns or watches. Surfaces team-wide announcements that would otherwise drown in volume.

```
# Issued in parallel, one per address in profile.m365.dl_addresses[]
outlook_email_search(
  recipient="team-all@example.com",
  afterDateTime=${state.last_run},
  limit=25
  # note: 'order' is incompatible with 'recipient' on this tool — orchestrator sorts post-fetch
)
```

Empty render: hidden when not configured.

#### M365.6 — M365 connectivity / auth healthcheck

**Cost:** XS · ~800ms · one call at brief start (always-on infra).

Confirms the M365 MCP is registered AND the user is authenticated. A 401 means registered-but-not-authed → render the auth-needed header. Always runs when the `m365` block is present in the profile.

The tool requires at least one filter param — `order="newest"` is the cheapest that satisfies that without narrowing the search. Successful response also includes `totalResultCount` (inbox size), which can be surfaced as a bonus stat if useful.

```
outlook_email_search(order="newest", limit=1)
```

Failure render: header note `⚠ M365 offline — run /mcp to authenticate Microsoft 365.`

#### M365.7 — Today's calendar meetings

**Cost:** M · ~600ms · one call.

Calendar events scheduled for today — meeting prep at a glance. Drives the brief's agenda line.

The tool accepts natural-language dates (`"today"`, `"tomorrow"`) and interprets them in the user's local timezone. For predictability, prefer explicit ISO bounds derived from the orchestrator's current time: `afterDateTime` = today 00:00 in user TZ, `beforeDateTime` = tomorrow 00:00 in user TZ. The natural-language form is acceptable as a fallback.

`query="*"` (or omit) is the wildcard that returns all events in the window — without a query the tool falls back to relevance ranking, which is wrong for a chronological agenda. `order="oldest"` sorts earliest-first.

```
outlook_calendar_search(
  query="*",
  afterDateTime="today",
  beforeDateTime="tomorrow",
  order="oldest"
)
# Returned fields per event: subject, organizer, attendees[], start, end,
#   location, isAllDay, isCancelled, isOrganizer, webLink.
# Orchestrator skips events where isCancelled == true.
```

Empty render: *"No meetings today."*

## Out of scope for this addon (deferred to future M365 catalog rounds)

The connector exposes these surfaces in the same namespace and behind the same auth, so they belong as **future M365 catalog entries** under this same addon — not separate addon files. Listed here for visibility:

- **Calendar (free/busy across attendees)** — `find_meeting_availability`. Useful for "when can the team meet?" lookups. Future M365.8+. Today's agenda is already covered by M365.7.
- **Teams chat** — `chat_message_search`. Unread mentions in channels and DMs. Future entries.
- **SharePoint** — `sharepoint_search`, `sharepoint_folder_search`. Documents and pages updated in window. Future entries.
- **Utility** — `read_resource`. Not its own catalog entry — used as `me-gala` (fullbody) expansion to fetch full content from search-returned URIs (e.g. a mail body, a calendar event description).

### Deferred email queries

Surfaced during the email-surface investigation but **not implementable on this connector**:

- **Flagged mail** — `outlook_email_search` exposes no `isFlagged` or `flagStatus` filter. Implementing via per-message `read_resource` is too expensive without a way to pre-narrow. Re-add only if the connector adds flag filtering, or if a richer Graph adapter lands.
- **Awaiting your reply** — needs per-brief conversation-state tracking; orchestrator is stateless by design.
- **Threads with unread responses (Cc: included)** — substantially overlaps M365.1.
- **Self-reminders / follow-ups** — no exposed filter for `reminderMinutesBeforeStart` on this tool.
- **Delegation queue** — `mailboxOwnerEmail` parameter exists but the surface (which mailboxes the user can delegate-read) is undocumented on this connector; niche signal.

Revisit any of these if the connector grows the necessary filters (pending investigation).

## Failure mode

If `m365` is **absent** from the profile, the brief skips it silently. M365 is opt-in; no "you're missing this" nag.

If `m365` is **configured** but the adapter isn't available:

- **MCP not registered** → drop M365 section, header note `⚠ M365 offline — Microsoft 365 connector is not available.`
- **User not authenticated (401)** → drop M365 section, header note `⚠ M365 offline — run /mcp to authenticate Microsoft 365.`
- **Graph throttling (429)** → render partial section, header note `⚠ M365: rate-limited by Microsoft 365. Results may be incomplete.`
- **Network timeout** → drop M365 section, header note `⚠ M365 offline — timeout connecting to Microsoft 365.`
- **One of N parallel calls fails** (e.g. one client domain times out) → render the rest, append `⚠ M365: 1 of N domain queries timed out.` to the header.

Never silent when the user expects M365 data. See SKILL.md "Visible failure modes" rule.

## Barista onboarding

The barista asks about M365 only when it's plausibly in use (user said yes to "use Microsoft 365 in your brief?").

Onboarding is light by design — two optional questions:

1. *"Any client domains we should treat as priority? For example `acme.com` or `globex.net`. Mail from these surfaces in its own section regardless of read state — easier to spot stakeholder pings. Skip if you don't have external clients."* — captures into `m365.client_domains[]`. Empty ok.
2. *"Any specific senders that should always surface — your CEO, a key partner, anyone where you don't want to miss a single email?"* — captures into `m365.important_senders[]`. Empty ok. Sofia suggests skipping this on first run; it's easy to add later via a tailoring nudge or `/cafe barista`.

`internal_domains[]` and `dl_addresses[]` are NOT asked on first run — they live behind opt-in via `/cafe barista calls` or a tailoring nudge.

If the user says they don't want M365 in the brief, the barista omits the `m365` block entirely from the saved profile.
